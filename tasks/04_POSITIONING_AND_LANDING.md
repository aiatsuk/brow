# Task 04 — Positioning, messaging, and landing-page proof

## Objective

Design a credible public narrative for `brow` based on what is shipped and measurable. Produce a landing-page information architecture, not final visual design.

## Required local inputs

- `README.md`
- `skills/browser/SKILL.md`
- `docs/research/01-SUMMARY-RU.md`

## Required external research

Inspect current landing pages and docs navigation for these eight direct/adjacent targets: Playwright CLI/MCP, Chrome DevTools MCP, Browser Use, Stagehand, Vercel agent-browser, open-gsd/gsd-browser, gstack browse, and Crawlee. Record headlines, primary CTA, evidence pattern, installation friction, security language, and developer trust signals.

## Required questions

1. What category should `brow` claim without misleading users?
2. What one-sentence promise is supported today?
3. Which claims require benchmarks or must be weakened?
4. How should “local-first,” “persistent,” “direct CDP,” “real input,” and “no raw CDP” be translated into user outcomes?
5. What should the landing page explicitly say it does not do?
6. What demo and artifact would provide the strongest proof?

## Task-specific deliverables

- Three positioning options with audience, headline, subhead, CTA, proof, risk.
- Recommended landing-page section order and exact content purpose for each section.
- Claims ledger: safe-to-publish, requires-proof, prohibited-now.
- One timestamped 6–10-scene demo script with narrated runtime of 80–100 seconds, explicitly marking live commands versus pre-recorded output, using only shipped commands.

## Task-specific acceptance criteria

- Do not use “secure,” “safe,” “stealth,” “undetectable,” “complete,” or “first” without narrowly scoped evidence.
- Do not imply daemon-restart persistence, OOPIF completeness, strict no-egress, or Windows support.
- Every recommended proof maps to a reproducible command or artifact.
