# Rust Implementation Stack: crates, codegen, IPC, storage, testing

> **Bottom line.** Write our own CDP client — but steal the codegen. No published Rust CDP crate (chromiumoxide 0.9.1, headless_chrome 1.0.22, chromey 2.54.0, cdpkit 0.5.0) supports `--remote-debugging-pipe` today; all of them are WebSocket-only, which is exactly the transport this project bans for security reasons. chromiumoxide additionally pulls 118 crates and 31s of clean build time for a hello-world, drags in `reqwest` unconditionally, and pins a CDP revision (1566079) that is ~5 Chrome majors behind the local Chrome 151. What chromiumoxide *does* have that is worth taking is `chromiumoxide_pdl` (MIT/Apache-2.0) — a PDL parser + `quote`-based generator with `.experimental()` / `.deprecated()` filters and a "regenerate-and-panic" freshness test that is the right pattern for a checked-in generated file. For plumbing: `command_fds` 0.3.3 + `tokio::process::Command` + `tokio::net::unix::pipe` is a verified-working, zero-`unsafe`-in-our-code replacement for the hand-rolled `pre_exec`/`dup2`/blocking-thread transport currently in `src/`. For IPC stay on `tokio::net::UnixListener` + NDJSON (`interprocess` only when Windows lands). For storage use **SQLite via `rusqlite` 0.40.1 (`bundled`) for job/graph/ref state, plus append-only JSONL for the event log** — redb/fjall are excellent but single-process-only and unreadable without our binary. Keep the workspace at **4–5 crates, not 14**. And: *the current `main` does not compile* (`input::hit_test` missing) — put a CI gate in before anything else.

### The decisive facts

1. **No pipe transport anywhere.** `--remote-debugging-pipe` support in chromiumoxide is [PR #325](https://github.com/mattsse/chromiumoxide/pull/325), opened 2026-06-03 by MidasLamb, still a **draft** with an unticked "created unit tests" box and an explicit *"I cannot test the windows part"*. Its author reached for exactly the two tools this dossier recommends: `tokio::net::unix::pipe` and `command_fds`. `gh search code --repo rust-headless-chrome/rust-headless-chrome "remote-debugging-pipe"` and the same for `spider-rs/chromey` return **zero results**.

2. **Protocol staleness.** `chromiumoxide_cdp/src/lib.rs` pins `pub const CURRENT_REVISION: Revision = Revision(1566079);`. Chromiumdash main-branch positions: Chrome 148 → 1610480, 149 → 1625079, 150 → 1639810, **151 → 1654411**. chromiumoxide's pin is *below* Chrome 148, i.e. roughly Chrome 145/146 — ~5 majors behind. Concretely, its PDL is missing four domains present in local Chrome 151: **`Ads`, `CrashReportContext`, `SmartCardEmulation`, `WebMCP`**. (Nothing in its PDL is absent from Chrome 151, so it is stale, not wrong.)

3. **Dependency weight.** `chromiumoxide` 0.9.1 with `default-features = false` still lists `reqwest = { version = "0.13", default-features = false }` as a **non-optional** dependency. A hello-world binary depending on it compiles **118 unique crates / 146 units in 31.27 s wall (79.5 s CPU)** on this M-series Mac, of which `chromiumoxide_cdp` alone is **19.50 s**. The current single-crate `brow` is 61 crates / ~7 s.

4. **Ergonomic mismatch.** chromiumoxide's generated event machinery (`Arc<dyn Event>`, `downcast_arc`, sealed traits, `CustomEvent`) exists to support a Puppeteer-shaped API. This harness wants the opposite: a narrow vetted capability surface where raw CDP is structurally unreachable (`src/ipc.rs` already encodes this and even has a test asserting no request variant can carry a method name). Wrapping chromiumoxide would put a full CDP surface one `use` away from every call site.

> **Honest counterpoint.** If the project ever wants Firefox/WebKit, or if the maintenance cost of tracking CDP drift becomes real, the calculus changes. But CDP drift is a codegen problem, not a client problem — and we are taking the codegen.

## 2. Protocol codegen

### PDL vs JSON

Both exist for the same protocol.

- **JSON** — `/json/protocol` from a live browser (1,605,774 bytes on Chrome 151; 746 KB when the per-domain objects are re-serialised compactly), and `browser_protocol.json` / `js_protocol.json` in the [devtools-protocol repo](https://github.com/ChromeDevTools/devtools-protocol). Trivially parsed with `serde_json`. **Ground truth for what *your* browser supports.**
- **PDL** — the upstream authoring format (`pdl/browser_protocol.pdl` + `pdl/domains/*.pdl`, `pdl/js_protocol.pdl`). `browser_protocol.pdl` is a 1 669-byte index of `include domains/X.pdl` lines. Richer comments; needs a parser.

**Recommendation: JSON, dumped from the pinned Chrome at codegen time.** The `/json/protocol` endpoint is the only source that tells you what the binary on *this machine* actually implements, and this project already launches Chrome anyway. Keep `protocol/browser_protocol.json` + `protocol/js_protocol.json` checked in (as the planned repo layout says), refreshed by an `xtask`. PDL parsing buys nothing once you drop chromiumoxide's parser and keep only its emitter ideas.

### Checked-in vs `build.rs` — argue for checked-in

`build.rs` codegen into `OUT_DIR` fails on every axis that matters here:

| Axis | `build.rs` → `OUT_DIR` | Checked-in `cdp.rs` |
|---|---|---|
| Offline / hermetic build | fragile (chromiumoxide's freshness check literally `reqwest::get`s GitHub) | ✅ |
| `git diff` shows protocol drift | invisible | ✅ — a Chrome upgrade shows up as a reviewable diff |
| rust-analyzer / goto-definition | mediocre in `OUT_DIR` | ✅ |
| Clean-build cost paid by every consumer | yes | no |
| `cargo package`/vendoring | needs `include` gymnastics | ✅ |
| Risk | — | the file can go stale silently |

The staleness risk is neutralised by chromiumoxide's own pattern, which is worth copying verbatim:

```rust
// xtask or crates/cdp-protocol/tests/generate.rs
#[test]
fn generated_code_is_fresh() {
    let dir = Path::new(env!("CARGO_MANIFEST_DIR"));
    let tmp = tempfile::tempdir().unwrap();
    Generator::default()
        .out_dir(tmp.path())
        .experimental(true)          // default in chromiumoxide
        .deprecated(false)           // default in chromiumoxide
        .allowed_deprecated_type("emulateNetworkConditions")
        .allow_list(include_str!("../protocol/allow.toml"))   // ours
        .compile_json(&[dir.join("../protocol/browser_protocol.json"),
                        dir.join("../protocol/js_protocol.json")])
        .unwrap();

    let new = fs::read_to_string(tmp.path().join("cdp.rs")).unwrap();
    let src = dir.join("src/cdp.rs");
    if new != fs::read_to_string(&src).unwrap() {
        fs::write(src, new).unwrap();
        panic!("generated code in the repository is outdated, updating...");
    }
}
```
*(shape taken from [`chromiumoxide_cdp/tests/generate.rs`](https://github.com/mattsse/chromiumoxide/blob/main/chromiumoxide_cdp/tests/generate.rs))*

The test **writes the fix and then fails**, so `cargo test` once is the whole update workflow, and CI catches the un-committed diff.

### Annotations, enums, optionals — and size

chromiumoxide's `Generator` (in `chromiumoxide_pdl/src/build/generator.rs`) is the reference implementation:

```rust
with_experimental: bool,               // default true
with_deprecated: bool,                 // default false
allowed_deprecated_type: HashSet<String>,
```
and the filters are literal `.filter(|d| with_deprecated || !d.deprecated)` / `.filter(|d| with_experimental || !d.experimental)` applied at domain, type, command and **parameter** level, plus `#[deprecated]` attribute emission on deprecated domains. Its own doc warns: *"Disabling experimental types may result in missing type definitions."* That warning is load-bearing — on Chrome 151, **38 of 57 domains are marked experimental**, including `Accessibility`, `CSS`, `DOMSnapshot`, `Storage`, `Overlay`, `LayerTree`, `Preload`, `WebAuthn`. This harness *requires* most of them. **So: `experimental = true` is mandatory, and every experimental method we call must be listed in a stability ledger with a Chrome-version note.**

Numbers you need for sizing (Chrome 151.0.7922.72, protocol 1.3, measured):

```
domains 57 | commands 669 | events 237 | types 616 | command params 1194
experimental domains 38 | experimental commands 207 | deprecated commands 40
```

And the size trap: the 25 domains a harness like this plausibly needs (`Browser, Target, Page, DOM, DOMSnapshot, CSS, Accessibility, Input, Runtime, Network, Fetch, Log, Console, Emulation, Storage, Security, ServiceWorker, Overlay, Performance, Tracing, IO, LayerTree, DOMDebugger, Debugger, HeadlessExperimental`) are **76 % of the protocol by bytes** — 495 commands, 157 events, 408 types. Domain filtering is not a size strategy. Only a **method-level allow-list** is:

```toml
# protocol/allow.toml — this file IS the capability boundary
[Page]
commands = ["navigate", "captureScreenshot", "getFrameTree", "getLayoutMetrics",
            "enable", "addScriptToEvaluateOnNewDocument", "createIsolatedWorld",
            "startScreencast", "stopScreencast", "screencastFrameAck"]
events   = ["frameNavigated", "loadEventFired", "lifecycleEvent", "screencastFrame"]

[Input]
commands = ["dispatchMouseEvent", "dispatchKeyEvent", "dispatchTouchEvent",
            "dispatchDragEvent", "insertText", "imeSetComposition", "synthesizePinchGesture",
            "synthesizeScrollGesture", "synthesizeTapGesture", "setIgnoreInputEvents"]
```

Emit `#[non_exhaustive]` on response structs so a Chrome upgrade that adds a field is not a breaking change, keep `Option<T>` for every PDL `optional`, emit `#[serde(rename_all = "camelCase")]` at struct level plus explicit `#[serde(rename)]` for the ~dozen names that don't round-trip (`url`, `id`, `x`, `y` are fine; `nodeId` vs `node_id` is handled by `camelCase`), and generate string-valued enums as `#[non_exhaustive] enum X { Known, .., #[serde(other)] Other }` — CDP adds enum variants constantly and `#[serde(other)]` prevents a Chrome upgrade from becoming a deserialisation panic.

Realistic budget: an allow-list of ~120 commands + ~40 events lands around **35–45 k lines / ~1.8 MB**, compiling in roughly **7 s** rather than 19.5 s.

> **Corrected 2026-08-04:** the original estimate was **8–15 k lines / <1 MB** and is a **2.5–4.7× underestimate on lines**. Measured the transitive `$ref` closure directly against the Chrome 151 `/json/protocol` dump. A *tighter-than-budget* allow-list — **93 commands + 33 events** across 20 domains, hand-built from the verb→CDP table in `80-security-capabilities-and-policy.md` — drags in **269 of 616 types (44 %)** and **34 % of the protocol by compact bytes**. Extrapolating linearly from the one measured point (chromiumoxide: 111,037 lines / 5,189,142 B / 19.50 s = 100 %):
> ```
> 93 cmds + 33 events -> type closure 269/616 (44%) -> 34% of bytes
>   ~37,900 lines | ~1.77 MB | ~6.7 s compile
> ```
> A more realistic 195-command list (the full capability surface incl. `storage`, `mutate`, `control` verbs) reaches **381/616 types (62 %) and 56 % of bytes → ~62 k lines / ~2.9 MB / ~11 s**. The author's own flagged risk (*"could be 2-3x my estimate"*) was correct and if anything optimistic. **Type closure, not command count, is what sizes the generated file** — `Network.Request` alone transitively pulls in most of the `Network` type graph. The *compile-time* half of the claim ("single-digit seconds") survives; the *size* half does not. Budget `cdp.rs` as a ~2 MB checked-in file and make sure `.gitattributes` marks it `linguist-generated` and `-diff` by default.

## 3. Async runtime and process plumbing

### Runtime

`tokio` 1.53.1. No reason to consider anything else: `smol`/`async-std` have no upside here and `async-std` is deprecated. Feature set for the daemon:

```toml
tokio = { version = "1.53", features = [
  "rt-multi-thread", "macros", "net", "io-util", "sync", "time", "fs",
  "signal", "process",            # <-- add: currently missing from Cargo.toml
] }
```
The current `Cargo.toml` omits `process`, which is why `browser/launch.rs` uses `std::process::Command` and hand-rolls everything.

### Handing fds 3 and 4 to Chromium on Unix — **use `command_fds`**

Chromium's contract, straight from [`content/public/common/content_switches.cc`](https://raw.githubusercontent.com/chromium/chromium/main/content/public/common/content_switches.cc):

```c
// Enables remote debug over stdio pipes [in=3, out=4] or over the remote pipes
// specified in the 'remote-debugging-io-pipes' switch.
// Optionally, specifies the format for the protocol messages, can be either
// "JSON" (the default) or "CBOR".
const char kRemoteDebuggingPipe[] = "remote-debugging-pipe";
```
So: **child reads fd 3, writes fd 4, NUL-delimited**, and `--remote-debugging-pipe=CBOR` is a supported (undocumented-elsewhere) alternative encoding.

Three ways to get fds 3/4 into the child:

| Approach | Verdict |
|---|---|
| `unsafe pre_exec` + `libc::dup2` (what `src/browser/launch.rs` does today) | Works, but ~30 lines of `unsafe`, three manual `close()` paths, and no handling of the case where a source fd already *is* 3 or 4 (then `dup2` clobbers it). It also can't use `tokio::process::Command` without duplicating the unsafe. |
| **`command_fds` 0.3.3, feature `tokio`** | **Recommended.** Deps: `nix ^0.31.2`, `thiserror ^2`, optional `tokio ^1.51`. Handles fd collisions, CLOEXEC, and works on both `std::process::Command` and `tokio::process::Command`. |
| `posix_spawn_file_actions_*` | Not exposed by std; no gain. |

Working code, **verified against Chrome 151** (note the import: the trait lives at the crate root, `command_fds::tokio` is a private re-export module — importing `command_fds::tokio::CommandFdExt` is a compile error):

```rust
use command_fds::{CommandFdExt, FdMapping};   // NOT command_fds::tokio::CommandFdExt
use std::os::fd::OwnedFd;
use tokio::process::Command;

let (to_child_r,  to_child_w)  = os_pipe()?;   // we write fd3
let (from_child_r, from_child_w) = os_pipe()?; // we read  fd4

let mut cmd = Command::new(chrome);
cmd.arg("--remote-debugging-pipe")
   .stdin(Stdio::null()).stdout(Stdio::null()).stderr(Stdio::piped())
   .kill_on_drop(true);

cmd.fd_mappings(vec![
    FdMapping { parent_fd: to_child_r,   child_fd: 3 },  // OwnedFd, moved
    FdMapping { parent_fd: from_child_w, child_fd: 4 },
])?;

let mut child = cmd.spawn()?;

let mut w = tokio::net::unix::pipe::Sender::from_owned_fd(to_child_w)?;
let mut r = tokio::net::unix::pipe::Receiver::from_owned_fd(from_child_r)?;
```
`FdMapping.parent_fd` is an `OwnedFd` (0.3.x changed this from `RawFd`), so the parent's copies are closed for you on spawn — the leak-on-spawn-failure branch in the current code disappears.

For the reader side, `tokio_util::codec::FramedRead` with a trivial `Decoder` that splits on `0x00` replaces the manual `Vec` scan and gives you backpressure for free (the current `mpsc::unbounded_channel` gives none — a page firing `Network.responseReceived` at 5 kHz will grow that channel without bound).

**Do not use `--remote-debugging-pipe=CBOR` yet.** It halves parse cost on big `DOMSnapshot` payloads but there is no maintained Rust CBOR-CDP decoder and the framing differs (length-prefixed, not NUL-delimited). Revisit only if profiling says JSON parsing is the bottleneck.

### Windows

Confirmed from the same Chromium file, guarded by `BUILDFLAG(IS_WIN)`:

```c
// Specifies pipe names for the incoming and outbound messages on the Windows
// platform. This is a comma separated list of two pipe handles serialized as
// unsigned integers, e.g. "--remote-debugging-io-pipes=3,4".
const char kRemoteDebuggingIoPipes[] = "remote-debugging-io-pipes";
```

So on Windows you pass **HANDLE values as decimal integers in the switch itself**, and the handles must be inheritable. There is no `command_fds` equivalent. The path is:

1. `CreatePipe` twice with `SECURITY_ATTRIBUTES { bInheritHandle: TRUE }` (or `SetHandleInformation(h, HANDLE_FLAG_INHERIT, HANDLE_FLAG_INHERIT)`).
2. Spawn with `bInheritHandles = TRUE` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` naming exactly those two handles (otherwise you leak every inheritable handle in the process).
3. Pass `--remote-debugging-pipe --remote-debugging-io-pipes=<h_in>,<h_out>` where the numbers are `handle as usize`.

`std::os::windows::process::CommandExt` in Rust 1.97 gives you `raw_attribute()` (stable since 1.72? — **unverified**, check `std::os::windows::process::ProcThreadAttributeList`) for the handle list; otherwise drop to `windows-sys` `CreateProcessW` directly. Budget this as a real 2–3 day task, not a port. chromiumoxide's PR author explicitly punted on it.

## 4. IPC: `browserctl` ↔ `browserd`

### Transport

| Option | Notes |
|---|---|
| **`tokio::net::UnixListener`** | What the repo does today. Zero extra deps, `peer_cred()` works. **Keep.** |
| `interprocess` 2.4.3 (2026-08-01, 0BSD OR Apache-2.0, MSRV 1.75, feature `tokio`) | The right answer *when Windows ships*. `local_socket` abstracts UDS ↔ Windows named pipes. Note 2.x removed its own UDS types in favour of std's. |

### Framing

Keep **newline-delimited JSON**. `serde_json` escapes `\n` inside strings, so "one line == one message" is an invariant, and `src/ipc.rs` already unit-tests it (`requests_round_trip_as_single_lines`). Length-prefixed framing buys nothing until you carry binary blobs inline — and you shouldn't: **screenshots and video go to files under `~/.brow/artifacts/…`, and the response carries a path.** A 12 MB full-page PNG base64'd through a JSON line is 16 MB of allocation on both sides.

Use `tokio_util::codec::{FramedRead, LinesCodec}` with `LinesCodec::new_with_max_length(1 << 20)` so a malformed peer cannot OOM the daemon.

### Streaming `--follow` and backpressure

The daemon should answer a `Follow`-shaped request with a **stream of NDJSON frames on the same connection**, terminated by a final `{"status":"ok"}`:

```json
{"kind":"event","seq":41,"ts":"2026-08-04T18:21:07.412Z","type":"console","level":"error","text":"…"}
{"kind":"event","seq":42,"…"}
{"status":"ok","data":{"followed":2,"truncated":false}}
```

Backpressure rules that matter:

- Per-connection `mpsc::channel(1024)` — **bounded**. Never `unbounded_channel` on a path fed by the browser. (`src/cdp/transport.rs` and `src/cdp/conn.rs` currently use unbounded; that is a latent OOM on a chatty page.)
- On `send().await` blocking >N ms for a *follower*, drop oldest and emit `{"kind":"lag","dropped":N}` — a slow `--follow` consumer must never stall CDP ingestion.
- On CDP ingestion, blocking is correct: if the daemon can't keep up, letting the pipe fill applies backpressure to Chrome, which is the desired behaviour.

### Socket path, permissions, and peer auth

The current choice — `~/.brow/run/brow.sock` inside a `0700` directory, with an explicit `sun_path` length test — is **right**, and the comment about `XDG_RUNTIME_DIR` overflowing macOS's 104-byte `sun_path` is a real hazard (macOS's `$TMPDIR` is `/var/folders/xx/……/T/`, easily 50+ chars). Two refinements:

1. Also `chmod 0600` the socket file itself after bind (belt and braces; the directory mode is the real control but a `0700` dir with a `0666` socket looks wrong in an audit).
2. **Check `peer_cred()` on accept and reject any uid != our own.** Verified on macOS: `UnixStream::peer_cred()` returns `uid`, `gid`, **and a real `pid`** — see §*empirical*. Widely-repeated claims that macOS gives no pid (because `getpeereid(2)` doesn't) are **wrong for tokio**, which uses `LOCAL_PEERPID`. The pid is genuinely useful: log which agent process issued a `mutate` capability call.

Abstract sockets (Linux, leading `\0` in `sun_path`) — **do not use them.** They ignore filesystem permissions entirely; any process in the same network namespace can connect. For a daemon holding logged-in browser sessions that is a security downgrade, and it buys only "no stale socket file", which a `flock`'d pid file solves better.

## 5. CLI

`clap` 4.6.5 + `clap_complete` 4.6.8, derive API. For a verb-noun surface this size the pattern is nested `#[derive(Subcommand)]` enums:

```rust
#[derive(Parser)]
#[command(name = "brow", version, propagate_version = true)]
struct Cli {
    /// Machine-readable output. Implies --no-color.
    #[arg(long, global = true)]
    json: bool,
    #[arg(long, global = true, default_value = "default")]
    session: String,
    #[command(subcommand)]
    cmd: Cmd,
}

#[derive(Subcommand)]
enum Cmd {
    Open(OpenArgs),
    #[command(subcommand)] Job(JobCmd),
    #[command(subcommand)] Page(PageCmd),
    #[command(subcommand)] Map(MapCmd),
}

#[derive(Subcommand)]
enum JobCmd {
    Start(JobStartArgs),
    Status { id: String },
    Logs { id: String, #[arg(long)] follow: bool },
    Artifacts { id: String },
    Pause { id: String }, Resume { id: String }, Stop { id: String },
    Approve { id: String, #[arg(long)] step: Option<u32> },
}
```

- `--json` **global**, and every command must have a stable JSON shape. Agents parse this; treat it as API and version it (`ipc::PROTOCOL_VERSION` already exists — surface it in `brow --json version`).
- Exit codes: `0` ok, `1` generic error, `2` clap usage error (clap's default), and reserve **`3` daemon-not-running**, **`4` capability-denied**, **`5` waiting-for-approval**, **`6` stale-ref / needs-resnapshot**, **`7` timeout**. Agents branch on these; a single `1` forces them to string-match.
- Completions: static `clap_complete::generate` for bash/zsh/fish/pwsh/elvish shipped as files. `clap_complete::env::CompleteEnv` (dynamic, `COMPLETE=zsh brow`) would let you complete live session names and `@node-42` refs — but it is behind the **`unstable-dynamic`** feature and the docs warn the shell↔binary interface is unstable. **Verdict: ship static now; revisit dynamic when it stabilises.**
- Use `#[derive(ValueEnum)]` for capability modes so `--mode inspect` is validated and self-documenting.

## 6. Storage

What has to be stored, and it is not one thing:

| Data | Shape | Access pattern |
|---|---|---|
| Job records | ~KB each, mutable state machine (`running`/`paused`/`waiting_for_approval`/`done`) | random update, list, query by status |
| Event log (console/network/route/action) | append-only, high volume (10³–10⁵/job), timestamped | append + range scan + tail |
| Site graph (nodes, edges, evidence, coverage) | relational: edges reference nodes, screenshots, requests | joins, "which routes are `discovered` but not `observed`" |
| Ref table (`@node-42` → backendNodeId + doc generation) | ephemeral, per-snapshot, invalidated on navigation | in-memory, rebuilt each snapshot |

### Comparison

| Option | Version / date | Crash safety | Concurrent readers | External deps | Human-readable | Verdict |
|---|---|---|---|---|---|---|
| **`rusqlite`** | 0.40.1 (2026-06-06), `libsqlite3-sys` 0.38.1 | WAL, battle-tested | ✅ multi-process | `bundled` compiles SQLite C via `cc` (needs a C compiler at build time, nothing at runtime) | ✅ `sqlite3 jobs.db` | **Yes, for job + graph state** |
| `libsql` | 0.10.0-**pre.4** (2026-06-02) | — | — | — | — | No — prerelease |
| `sqlx` | 0.9.0 (2026-05-21) | via SQLite | ✅ | async + compile-time query checking (`DATABASE_URL` at build time — hurts hermetic builds) | ✅ | Overkill; `rusqlite` on `spawn_blocking` is simpler |
| `redb` | 4.1.0 (2026-04-19) | ✅ ACID, crash-safe by default, MVCC readers-with-writer | ❌ **single process** (maintainer, issue #838: *"You'll need to wrap it in an IPC layer"*) | pure Rust ✅ | ❌ | No |

### Recommendation

**SQLite (`rusqlite` 0.40.1, features `["bundled", "backup", "functions"]`) for `~/.brow/state.db` + JSONL for the event log.**

```
~/.brow/
  state.db                        # jobs, sessions, site graph, coverage, approvals
  state.db-wal  state.db-shm
  artifacts/<session>/<job>/
    events.jsonl                  # append-only, fsync'd every N ms
    actions.jsonl                 # the action log the video is synced to
    frames/000001.jpg …
    video.mp4
    shots/*.png
```

Reasons, in order:
1. The site graph is **relational** — edges → nodes → evidence → requests, with queries like "routes with status `discovered` and no `observed` edge". Writing that on a k/v store means hand-rolling secondary indices.
2. A user must be able to open the DB with `sqlite3` when the daemon is wedged. redb/fjall files are opaque.
3. `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;` gives you concurrent readers *from another process* — which is how a future `brow inspect --readonly` or an external dashboard works without going through the socket.
4. JSONL for events because: `tail -f` works, a torn last line is trivially recoverable (drop it), and it costs nothing. Store `(job_id, seq_lo, seq_hi, byte_offset)` checkpoints in SQLite so `--follow --since` can seek instead of scanning.

**The `bundled` tradeoff, stated honestly:** `rusqlite/bundled` compiles the SQLite amalgamation via the `cc` crate — and it requires a C toolchain

> **Corrected 2026-08-04:** the original text said *"roughly 15–25 s added to a clean build"*. **Measured on this machine** (M-series, rustc 1.97.1), a pristine `cargo new` + `cargo add rusqlite --features bundled` + `rm -rf target`:
> ```
> clean debug build   : 2.97 s total  (libsqlite3-sys unit = 1.48 s, 17 units)
> clean release build : 13.61 s total
> produced            : target/debug/build/libsqlite3-sys-*/out/libsqlite3.a  =  4,141,776 bytes
> ```
> So `bundled` costs ~**3 s** on a debug build, not 15–25 s — an order of magnitude cheaper than stated and **not** a reason to reconsider. The C-toolchain requirement is the only real objection that survives. (present on any machine with Xcode CLT or build-essential; **absent on a bare `rust:alpine` image**). The alternative (`libsqlite3-sys` linking the system SQLite) is zero build cost but reintroduces "works on my machine". For a local-first developer tool, **bundle**.

Refs (`@node-42`) stay in memory in a `HashMap<RefId, (DocumentGeneration, BackendNodeId, FrameId)>` guarded by the generation counter. Persisting them is wrong — they are invalid the moment the page navigates, which is exactly the property the spec demands.

## 7. Artifacts

### Images

- **`image` 0.25.10** (2026-03-10) as the front door: decode the base64 from `Page.captureScreenshot`, crop for per-node shots, compose annotations, diff. Enable only the codecs you need (`default-features = false, features = ["png", "jpeg", "webp"]`) — the default feature set drags in AVIF/`ravif`/`rav1e`, which is a large compile.
- **`png` 0.18.1** directly if you want to skip `image`'s `DynamicImage` for the common "save what Chrome gave us" path — but Chrome already returns PNG bytes, so the fastest path is `fs::write` with no decode at all. Decode only when cropping/diffing.
- **Image diff**: do it yourself. A per-pixel ΔE or simple RGB-distance with a tolerance and a small blur is ~60 lines and avoids `dssim`/`image-compare` deps. Emit both a diff PNG and a `{ "changed_px": n, "total_px": m, "ratio": r, "bbox": [...] }` record — the ratio is what a test asserts on, the PNG is what a human looks at.
- **`oxipng` 10.1.1** optionally, behind a flag, to shrink stored screenshots. Not by default (it is slow).

### Video

This is the honest part. **There is no production-grade pure-Rust H.264 encoder.** The options:

| Option | Version | Assessment |
|---|---|---|
| **`ffmpeg-sidecar` 2.5.2** (2026-05-30, MIT) | Shells out to the `ffmpeg` binary | **Recommended.** But **`default-features = false`** — its default feature is `download_ffmpeg` (pulls `ureq`, `zip`, `tar`, `xz2` and fetches a binary over the network). Keep `paths` for discovery, never `download`. |
| `ffmpeg-next` 8.1.0 (2026-03-18) | Safe bindings to system libav* | License is **WTFPL** (legally dubious for redistribution), links system FFmpeg → hard runtime dep, `bindgen` build. No. |

| `mp4` 0.14.0 | **2023-08-01** | Stale. |
| `re_mp4` 0.5.1 | 2026-07-08 | **Parser**, not a muxer (Rerun's). Wrong tool. |
| `openh264` 0.9.7 (2026-07-08, BSD-2) | Real H.264 encoder, Cisco's | Viable pure-ish path (`openh264-sys2` builds the C from source). Cisco's patent-royalty arrangement covers *their* binary, not one you compile — a licensing question for the owner, not an engineering one. |

**Degradation ladder (implement all three tiers):**

1. **ffmpeg present** (`which ffmpeg`, or `$BROW_FFMPEG`): `Page.startScreencast` → JPEG frames → feed `ffmpeg -f image2pipe -framerate <vfr> -i - -c:v libx264 -pix_fmt yuv420p video.mp4` on stdin via `ffmpeg-sidecar`. Because screencast frames are **variable-rate**, write a concat/timestamp sidecar rather than assuming constant fps — or pass `-vsync vfr` with explicit PTS.
2. ~~**ffmpeg absent, want a single playable file**: animated WebP via `image-webp` 0.2.4~~ — **this tier does not exist. Delete it from the plan.**

> **REFUTED 2026-08-04.** `image-webp` **0.2.4** (latest; published **2025-08-27**, i.e. ~1 year stale) **cannot encode animated WebP.** Downloaded and inspected the crate source:
> ```
> $ grep -rn "ANMF\|ANIM\b\|animation" image-webp-0.2.4/src/encoder.rs   ->  no matches
> $ grep -n "pub fn" image-webp-0.2.4/src/encoder.rs
>   632: pub fn new(w: W)              653: pub fn set_xmp_metadata(...)
>   643: pub fn set_icc_profile(...)   658: pub fn set_params(...)
>   648: pub fn set_exif_metadata(...) 667: pub fn encode(self, data, width, height, color)   <- ONE frame, consumes self

> `encode()` takes `self` by value and a single frame buffer; there is no `ANIM`/`ANMF` chunk writer anywhere in the crate. APNG is technically reachable (`png` crate has `set_animated`/`write_frame`), but an APNG of a 40-minute screen recording is not a serious artifact. **The degradation ladder is two tiers, not three: ffmpeg, or frames-on-disk.** That makes tier 3 (frames + `frames.jsonl`) the *only* guaranteed path and raises the priority of getting its manifest format right — see §*Limits*.
3. **Always, regardless**: write `frames/NNNNNN.jpg` + `frames.jsonl` (`{"seq":n,"ts_ms":…,"file":"…","metadata":{…}}`) and *state in the CLI output* that video muxing was skipped and how to produce it (`brow job artifacts <id> --mux`). ## 8. Observability inside the daemon

```toml
tracing = "0.1"
tracing-subscriber = { version = "0.3.23", features = ["env-filter", "json", "time"] }
tracing-appender = "0.2.5"
```

- Two layers: a human `fmt` layer to stderr (only when foregrounded) and a **JSON** layer to `~/.brow/logs/browd.log`. The JSON layer is what `brow logs --follow` tails and what a bug report attaches.
- Rotation: `tracing_appender::rolling::Builder` with `.rotation(Rotation::DAILY)`, `.filename_prefix("browd")`, `.filename_suffix("log")`, **`.max_log_files(7)`**. `Rotation` also has `minutely()`, `hourly()`, `weekly()`, `never()`. Wrap in `tracing_appender::non_blocking` and **hold the `WorkerGuard` for the process lifetime** — dropping it early silently swallows logs (the single most common tracing-appender bug).
- Instrument every capability call with `#[tracing::instrument(skip(self), fields(session, capability, job_id))]`. The daemon's audit trail for `mutate` operations is a *product requirement*, not just debugging — emit those at `INFO` with a stable `event = "capability.invoke"` field so they can be filtered out of the log into the job record.
- **Redaction must happen at ingest, not at log time.** The repo already has `src/redact.rs` doing this for events; the same must apply to tracing fields — never `tracing::debug!(?cookie)` or `?request_headers`.
- `RUST_LOG` / `BROW_LOG` via `EnvFilter`, default `browd=info,brow=warn`.

## 9. Testing a browser harness without flakiness

### The layer cake

| Layer | Tooling | Chrome needed? | Flaky? |
|---|---|---|---|
| Protocol codec (frame split, NUL boundaries, huge frames) | plain `#[test]` | no | never |
| CDP client semantics (id correlation, sessionId routing, error mapping, timeouts) | **mock protocol stream** over an in-memory duplex | no | never |
| Page tree / snapshot shape | **golden files** via `insta` 1.48.0 | yes, once | low |
| Input synthesis | fixture page that records events | yes | low |
| Screenshots | fixture page + pixel diff with tolerance | yes | **medium** |
| Crawler / site graph | fixture SPA | yes | medium |

### Mock CDP without a browser — the highest-leverage test asset

Make the transport a trait, not a struct:

```rust
pub trait CdpTransport: Send + 'static {
    fn send(&self, frame: Vec<u8>) -> Result<(), TransportClosed>;
    fn recv(&mut self) -> impl Future<Output = Option<Vec<u8>>> + Send;
}
```
Then a `ReplayTransport` reads a checked-in `fixtures/cdp/<scenario>.ndjson` recorded from a real session:

```json
{"dir":"out","t_ms":0,"frame":{"id":1,"method":"Page.enable","params":{},"sessionId":"A1"}}
{"dir":"in", "t_ms":12,"frame":{"id":1,"result":{},"sessionId":"A1"}}
{"dir":"in", "t_ms":340,"frame":{"method":"Page.frameNavigated","params":{…},"sessionId":"A1"}}
```
Record these with a `BROW_CDP_TRACE=<path>` env var in the real transport — the recorder is ~20 lines and gives you a regression corpus for free, plus a debugging tool ("send me your trace"). This is how you test `Runtime.evaluate` side-effect handling, `Target.attachedToTarget` races, and OOPIF session routing **deterministically**, none of which is testable reliably against a live browser.

### Fixture HTTP server

`axum` 0.8.9 bound to `127.0.0.1:0` (ephemeral port, returned from `TcpListener::local_addr()` — never a hardcoded port, that is the #1 CI flake). Serve pages from `fixtures/pages/`. Deterministic pages means:

- `prefers-reduced-motion` forced via `Emulation.setEmulatedMedia` **and** a CSS `*{animation:none!important;transition:none!important}` injected via `Page.addScriptToEvaluateOnNewDocument`.
- Fixed viewport + `deviceScaleFactor: 1` via `Emulation.setDeviceMetricsOverride`.
- No web fonts — system font stack only, or the same glyph renders differently across runners.
- Freeze time: `Runtime.evaluate` a `Date.now`/`performance.now` shim in the isolated world before load, or `Emulation.setVirtualTimePolicy` (EXPERIMENTAL, fiddly).
- `wiremock` 0.6.5 only if you need to assert on *outbound* HTTP; for fixture pages axum is simpler.

### Golden files

`insta` 1.48.0 with `INSTA_UPDATE=always cargo test` for the accept loop. Snapshot the page tree as **canonical JSON with volatile fields elided** — `backendNodeId`, `frameId`, `loaderId`, timestamps, and any absolute path must be replaced by stable placeholders or the snapshot changes every run. `insta`'s redaction feature (`insta::assert_json_snapshot!(tree, { ".**.backendNodeId" => "[id]" })`) does this declaratively.

### Screenshot diffing tolerance

Bluntly: **exact-match screenshot assertions across machines do not work.** macOS vs Linux font rasterisation, GPU vs SwiftShader compositing, and subpixel AA all differ. Policy:

- Assert on **structure** (bounding boxes from `DOM.getBoxModel` / `Page.getLayoutMetrics`) in cross-platform CI.
- Assert on **pixels** only against goldens generated on the same platform, with a tolerance: per-pixel channel delta ≤ 8/255 ignored, and fail if `changed_ratio > 0.001`.
- Store goldens per-platform (`fixtures/golden/{macos,linux}/…`) and let CI regenerate on the platform it runs on.
- Use `--force-device-scale-factor=1`, `--hide-scrollbars`, `--disable-lcd-text`, and `--font-render-hinting=none` to cut variance.

### CI

GitHub-hosted `ubuntu-24.04` **ships Chrome preinstalled** — the runner-images readme lists `Google Chrome 150.0.7871.128`, `Chromium 150.0.7871.0`, `ChromeDriver 150.0.7871.124` (an `ubuntu-26.04` image also exists now). So `browser-actions/setup-chrome` is optional; but **pin it** anyway so a runner-image bump doesn't silently change Chrome major under you. `--headless=new` needs no Xvfb. Suggested matrix: `{ubuntu-24.04, macos-latest} × {chrome-stable, chrome-beta}` with the beta leg `continue-on-error: true` as an early-warning for CDP drift. Gate on: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --lib` (no browser), then `cargo test --test '*'` (browser). Add `cargo deny check bans licenses` to enforce the "no Playwright/Puppeteer/Selenium anywhere in the graph" constraint mechanically — a `[bans] deny = [...]` list of `chromiumoxide`, `headless_chrome`, `thirtyfour`, `fantoccini`, `chromey` is the only way that constraint stays true after 20 dependency bumps.

## 10. Workspace ergonomics: 14 crates is wrong

The proposed split — `crates/{browserd, browserctl, cdp-protocol, cdp-transport, browser-process, sessions, input, inspection, events, capture, crawler, jobs, policy, artifacts}` — is over-fragmented for a project at 7 414 lines.

**Facts:** splitting a workspace does **not** reduce clean build time (same total codegen, plus per-crate metadata overhead). It helps *incremental* builds only when a leaf crate genuinely doesn't depend on the churny one. Here, `inspection`, `input`, `capture`, `crawler`, `events` would all depend on `cdp-protocol` + `cdp-transport` + `sessions`, so any change to the session model rebuilds everything anyway. Meanwhile you pay: 14 `Cargo.toml`s to version-bump, cross-crate `pub` surfaces where a private helper would do, and orphan-rule pain (you cannot `impl From<cdp::Node> for tree::Node` if those live in different crates you don't both own — you'll end up with a `-types` crate, then a `-core` crate, and the count grows).

**Recommendation — 4 crates:**

| Crate | Contains | Why separate |
|---|---|---|
| `brow-cdp` | generated `cdp.rs`, transport, connection/session multiplexer, browser launch | The only crate with a huge generated file. Isolating it means editing the harness doesn't recompile 10 k lines of generated types. **This is the one split that pays for itself.** |
| `brow-core` | page tree, input, capture, events, crawler, jobs, policy, artifacts, storage | These share types constantly. Splitting them is all cost, no benefit. Use modules. |
| `brow` (bin) | CLI, IPC client, output rendering | Small, fast to rebuild, the thing you iterate on |
| `browd` (bin) | daemon, socket server, supervisor | ditto |
| `xtask` (bin, not in default members) | protocol fetch + codegen + release packaging | Keeps codegen deps (`reqwest`/`ureq`, `quote`, `prettyplease`) out of the real dependency graph |

Split further **only when a compile-time measurement says so**. `cargo build --timings` on the current tree, re-run after each 2 k lines, is the trigger. And note the current tree is a *single* crate with two binaries via `default-run` — moving to a workspace is cheap later, moving back from 14 crates is not.

Compile-time hygiene regardless of layout: `[profile.dev] debug = 1` (line tables only, ~30 % faster links), `[profile.dev.package."*"] opt-level = 2` (deps optimised once, your crate stays fast to build), consider `-Zshare-generics` on nightly-only CI, and `cargo +nightly udeps` in CI to catch dependency creep.

## Limits and impossibilities

Blunt list of places where the brief asks for something that is harder or different than it sounds — from *this* dimension only.

1. **"Daemon must survive independently of the calling terminal" is not a Rust problem, and `kill_on_drop(true)` actively fights it.** A launchd/systemd-managed daemon that owns Chrome must *not* kill Chrome when a supervisor restarts the daemon. You need explicit re-attach: persist the Chrome pid + a way to reconnect. **But CDP-over-pipe cannot be re-attached** — the fds die with the process that held them. So either (a) the daemon never restarts without killing its browsers, or (b) you accept a listening port for re-attachability, which the security model forbids. **This is a real, unavoidable tension. Recommendation: (a) — on daemon restart, `Browser.close` all children, then relaunch. Say so in the docs; do not pretend sessions survive a daemon restart.**

   > **Verified 2026-08-04, and the conclusion is now stronger than "cannot re-attach": the browser does not even survive to be re-attached to.** Chrome exits ~1.0 s after fd-3 EOF (empirical table #9). Daemon death ⇒ browser death is automatic, not something you have to arrange. `kill_on_drop(true)` is therefore redundant for Chrome, and the SCM_RIGHTS-to-a-supervisor escape hatch the author speculated about would *not* help either: the surviving supervisor would have to keep the write end open, which is precisely the orphan condition in #9b.
   >
   > **NEW, and this is a week-one bug:** the EOF guarantee holds **only if no other process holds a duplicate of the fd-3 write end.** Verified orphan (#9b): with `/bin/sleep 120` holding an inherited copy, Chrome was `STILL ALIVE after 40.2s`. `browserd` *will* spawn ffmpeg for `--record-video`. **Mandatory:** set `FD_CLOEXEC` on both CDP pipe fds and assert it in a unit test. `command_fds`' `FdMapping` consumes an `OwnedFd` and closes the parent copy on spawn, but the *retained* `Sender`/`Receiver` fds are the ones at risk — `tokio::net::unix::pipe::Sender::from_owned_fd` does **not** set CLOEXEC for you, and `std`'s `os_pipe`/`pipe2(O_CLOEXEC)` guarantee is lost the moment you `dup` or hand the raw fd anywhere. Keep the belt-and-braces orphan sweep (`ppid==1` + `--user-data-dir` match + `kill(-pgid)`) precisely for this case.
2. **No published Rust CDP crate can be used at all**, so there is no "buy" option — only "steal the codegen". The build-vs-buy call was made for us by the pipe requirement. Budget the CDP client as real work (~2 000–3 000 lines: transport, framing, id correlation, session routing, timeouts, error taxonomy, event fan-out).
3. **`--remote-debugging-io-pipes` on Windows is untested by anyone in the Rust ecosystem.** chromiumoxide's PR author explicitly declined to implement it. You will be first. Do not put Windows in a v1 milestone.
4. **No pure-Rust H.264 encoder exists at production quality in 2026.** Video is either ffmpeg-shelling or `openh264` (Cisco C, patent-adjacent) or frames-on-disk. There is no fourth option. The "must not hard-require ffmpeg" constraint therefore means **video is a best-effort artifact**, not a guaranteed one.

   > **Verified 2026-08-04 — worse than stated.** The animated-WebP escape hatch does **not** exist: `image-webp` 0.2.4's encoder has no `ANIM`/`ANMF` support and `encode()` handles exactly one frame (see §7). So without ffmpeg there is **no single-file video output at all**, only `frames/NNNNNN.jpg` + `frames.jsonl`. Design the frame manifest as the *primary* artifact and the mp4 as a derived render, and make `brow job artifacts <id> --mux` a first-class documented command rather than a footnote.
5. **`--json` output cannot be both stable and complete** while the page-tree model is evolving. Pick one: version the schema (`"schema": 3`) and accept breaking bumps, or freeze a minimal core and put everything else under an explicitly-unstable `"x"` key. Agents will build on whatever you emit.
6. **Cross-platform screenshot golden files are not achievable.** Anyone promising CI-portable pixel assertions is wrong. Structure assertions are portable; pixels are not.
7. **`experimental = false` in codegen is not an option.** 38 of 57 domains on Chrome 151 are experimental, including ones this project cannot function without (`Accessibility`, `CSS`, `DOMSnapshot`, `Storage`, `Overlay`, `LayerTree`). The harness is *built on* experimental CDP. That is a permanent maintenance liability, not a phase.
8. **redb/fjall/sled are all off the table for anything a second process might read**, and the "second process" here includes the user with `sqlite3`. The pure-Rust-no-C purity argument loses to operability.
9. **The event log cannot be both crash-perfect and fast.** JSONL with `fsync` per line is durable and slow (~100–1000 writes/s); batched `fsync` every 50 ms loses at most 50 ms of events on a hard kill. Take the batched option and document the window.

## Open questions for the owner

1. **The repo is not empty** (2 commits, 7 414 lines, single-crate `brow`) and **HEAD does not compile**. Is this dossier meant to (a) validate the existing direction, or (b) propose a rewrite? I have written it as (a) with concrete diffs.
2. **Do you want `command_fds` + `tokio::process` (my recommendation) or to keep the hand-rolled `pre_exec`/`dup2` + blocking-thread transport?** The hand-rolled version works and is well-commented; the tradeoff is 3 `unsafe` blocks and 2 threads/browser vs one 25 KB dependency (`nix` + `thiserror`, both already transitively present).
3. ~~**Chrome does not die on fd-3 EOF (verified).**~~ **Retracted — Chrome exits ~1.0 s after fd-3 EOF.** The revised question: are you willing to make `FD_CLOEXEC`-on-both-CDP-fds a hard, unit-tested invariant, plus keep an orphan sweep for the leaked-fd case? (Both are cheap; the alternative is intermittent 1 GB orphan browsers that only appear on video-recording jobs.)
4. **SQLite `bundled` (a C compiler at build time) — acceptable?** If the answer is "must build on `rust:alpine` with no cc", the answer flips to redb and we give up external readability.
5. **`openh264` (BSD-2, Cisco, H.264 patent pool) as the no-ffmpeg video path — in or out?** In means one C dependency and a licensing footnote. Out means video is ffmpeg-only.
6. **Crate count: 4 or 14?** I recommend 4 (+`xtask`). If you want 14 for conceptual clarity rather than build reasons, say so and I'll stop arguing — but measure `cargo build --timings` before and after.
7. **CBOR CDP framing (`--remote-debugging-pipe=CBOR`) — worth a spike?** Confirmed to exist in Chromium's switch documentation. Nobody in the Rust ecosystem has implemented it. Could be a meaningful win on `DOMSnapshot.captureSnapshot` payloads (multi-MB JSON), but it is a from-scratch decoder.
8. **What is the MSRV policy?** `Cargo.toml` says 1.82 but `chromiumoxide`/`headless_chrome` and `command_fds` are all on edition 2024 / MSRV 1.85. Bumping to 1.85 unlocks edition 2024 and costs nothing on a tool shipped as a binary.
